# GPUI Android：第 3 輪畫面停住的原因＋字型記憶體（2026-10-24，Asia/Taipei）

## 結論先看

1. **畫面停住的原因找到了，也修好了** ✅：gpui-mobile 只在 app「有輸入焦點」時才畫畫面。
   Android 上「沒焦點但還在畫面上」很常見（系統 ANR 對話框、SystemUI 當掉重啟、通知欄、多視窗）。
   焦點被搶走、又一直沒還回來時，GPUI 就整個停畫：報價照收、指標照算，畫面不動。egui 沒焦點也照畫，所以沒這問題。
   修補：改成「看得到（Start～Stop）且有畫面 surface 就畫」，不看焦點。
2. **記憶體 PSS 少了約 1/3** 🏆：系統字型原本整檔讀進記憶體（光中文字型 NotoSansCJK 就 32 MB），改成 mmap（作業系統按需載入、可共用、可回收）。
   - 報價表：**91.6 → 57.6 MB**（−34 MB）
   - 走勢圖：**93.6 → 61.4 MB**（−32 MB）
   - 這和 10/23 egui（glow）的 58／53 MB 已經同一級。
3. **不需要再做「延遲／子集載入中文字型」**：mmap 之後字型實際佔的記憶體約 7 MB，而且是檔案頁（記憶體吃緊時系統可以直接丟掉），再省也有限。

## 1. 畫面停住

### 怎麼確認的
- 停住時抓了：GPUI 的畫圖排程狀態（每秒一行 `PACER`）、Android 視窗狀態（`dumpsys window`）、焦點狀態（`dumpsys input`）、執行緒堆疊。
- 停住時全部長一樣：
  - 最後一個事件是 `LostFocus`，後面沒有 `GainedFocus`；
  - `canDraw=false`，畫面幀數停住（例如停在第 16 幀、之後 196 秒沒畫）；
  - 但 Android 說這個視窗**還在螢幕上**（`isVisible=true`、`mHasSurface=true`），而 InputDispatcher 說 `FocusedWindows: <none>`（系統那邊沒有任何視窗拿到焦點）；
  - 主執行緒沒卡住（在等事件），收報價的執行緒也正常。
- 10/23 跑 bench 時模擬器跳過「Process system isn't responding」（系統 ANR）對話框（截圖 `freeze-before/system-anr-2026-10-23.png`），就是這類「焦點被搶走」的情況。

### 修補前 vs 修補後（同一台模擬器、同樣的重圖表壓測）

觸發方式：壓測跑到一半把 SystemUI 程序砍掉（模擬它 ANR 被系統殺掉），或把手機時鐘往前撥。

| 觸發方式 | 修補前：畫面上凍住 | 修補後：畫面上凍住 |
|---|---|---|
| 砍 SystemUI | **2 次／6 輪** | **0 次／4 輪** |
| 時鐘往前撥 2800 秒 | **1 次／1 輪** | 沒測 |
| 不觸發，單純壓測 | 0／5 | 0／6 |
| 模擬器整台暫停 120 秒、時鐘往回撥 600 秒 | 0／3 | 沒測 |

- 「畫面上凍住」＝ app 視窗還在螢幕上，但幀數 40 秒以上不動。
- 修補後 4 輪砍 SystemUI：3 輪是砍完後系統跳回鎖定畫面，app 被系統收到背景（`Stop`、surface 被收走），本來就不用畫，這是正確行為；另 1 輪是 app 一啟動就被鎖定畫面蓋住，90 秒後回到前景就繼續畫（`canDraw=true`）。
- 修補前 6 輪裡另外 4 輪：2 輪沒凍住、1 輪鎖定畫面（同上，不算）、1 輪模擬器太慢沒啟動完。
- 這個觸發方式是隨機的（要剛好焦點沒還回來），所以次數不多；但修補前凍住時的狀態每次都一樣，原因很明確。
- 另外做了「開一個系統對話框蓋在 app 上 25 秒」的固定觸發，結果見下面「對話框測試」。

### 修補內容（`mobile/vendor/gpui-mobile`，詳見 `PATCHES.md`）
- 畫不畫改看「看得到＋有 surface」，不看輸入焦點。
- 焦點／前後景事件改成「最後一個為準」（原本同一輪先 Pause 再 Resume 固定順序處理，事件順序反過來時結果會錯）。
- 診斷：`XQ_PACER_LOG=1` 每秒印一行畫圖排程狀態，平常不開、不花成本。
- 要給 Longbridge（gpui-mobile 上游）的 issue 草稿在 `PATCHES.md`，還沒開，等 Tina 決定。

## 2. 字型記憶體

同一個 APK，用環境變數切換字型載入方式，各跑 3 輪取中位數（`mem/mem.jsonl`）。PSS 用 `/proc/<pid>/smaps_rollup` 量（`dumpsys meminfo` 在這台慢模擬器上常逾時；有讀到的幾次數字差不到 1 MB）。

| | 原本：整檔讀進 heap | 修補：mmap＋去重 | 差 |
|---|---|---|---|
| PSS，報價表 | 91.6 MB（91.3／91.6／92.1） | **57.6 MB**（57.6／57.6／58.4） | −34.0 MB |
| PSS，走勢圖 | 93.6 MB（93.6／93.4／94.0） | **61.4 MB**（61.4／61.3／63.7） | −32.2 MB |
| 　其中匿名記憶體（heap 等），報價表 | 74.8 MB | 34.0 MB | −40.8 MB |
| 　其中檔案頁（含字型），報價表 | 16.1 MB | 22.9 MB | +6.8 MB |
| Native heap（dumpsys，報價表） | 58.4 MB | 17.6 MB | −40.8 MB |
| 載入的字型檔 | 11 個，42.8 MB | 9 個（去掉重複的捷徑），38.1 MB 映射 | |

- 匿名記憶體少了約 41 MB，換來約 7 MB 檔案頁（字型實際被讀到的部分）。檔案頁跟其他 app 共用，系統記憶體不夠時可直接丟掉，不用寫回。
- 和 10/23 表上的 GPUI 105／101 MB 不能直接相減：那次是 bench 腳本、不同時間點、用 dumpsys 量的。同一天、同一個 APK 的 A/B 是上表。
- 「只載入指定字型」的模式（`GPUI_ANDROID_FONTS=…`）這次**沒量到**：字型清單超過 Android system property 92 字元上限，設定沒生效，結果和 mmap 一樣，所以不列。從上表看，mmap 後字型本來就只佔約 7 MB，就算只載入一半也省不到幾 MB。

## 3. 其他可以再省／再改的地方（還沒做）

1. **畫圖排程只看焦點的同一個問題，`android/host.rs`（Java 主導的迴圈）也有**：本 app 沒用到，沒改；開 upstream issue 時一起提。
2. **重圖表在模擬器上 1.4 fps**：主要是軟體模擬 GPU，要真手機才看得出 GPUI 的真實表現。桌面版的 A2／A3（報價表一列一個 canvas、橫平豎直的形狀改畫方塊）可以搬到手機版。
3. **APK 大小**：arm64 15.4 MB（egui 6.7 MB）。可以試 `opt-level="z"`、去掉沒用到的 gpui-mobile 元件（material／glass 元件庫）、strip 符號。
4. **字型**：可以只放 Roboto＋NotoSansCJK＋emoji（清單改用短名稱或檔案設定，避開 92 字元限制）；省得不多，但啟動時少開幾個檔。
5. **啟動**：GPUI 啟動到第一筆報價約 13.7 秒（模擬器），其中 Vulkan 初始化和建字型資料庫佔多少還沒拆開量。
